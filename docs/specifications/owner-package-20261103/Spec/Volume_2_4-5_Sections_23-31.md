Volume 4 — System, Network & Hardware
23. Domain 10 — System / Network / Hardware (36 entries)
Domain 10 contains three functional worlds: system services (D10.01–D10.12), network services (D10.13–D10.24) and hardware services (D10.25–D10.36). Almost all of it is observation. Only D10.24 modifies anything, and it does so through the Repair Lab operation contract (Section 21 of Volume 3). Observation services are complete when they measure accurately and state what they cannot measure.
23.1 Shared Domain 10 rules (REQUIRED)
Rule
Requirement
Sample provenance
Every metric is {metric, value, unit, sampleTime, provider, source}. sampleTime is the time the OS produced the reading, not the time the UI rendered it. No interpolation, no synthetic backfill.
Freshness
Each card shows sample age and is marked stale when older than its refresh window. A stopped sampler shows the last real sample with an age marker.
Capability detection
Each provider reports available, partial, unsupported-platform, provider-missing or needs-elevation with a reason before any control is enabled. Missing sensors, absent batteries, no Wi-Fi radio and virtual machines are normal conditions, not errors.
No guessed values
A field a provider cannot supply is absent and rendered as — with the reason. Zero is never a placeholder for unknown.
Fixed queries only
Providers use fixed, typed queries (native API, performance counters, or a fixed CIM class and property list). Nothing from the renderer is concatenated into a command or query.
Active probes
D10.16 and D10.18 are the only services that send network traffic. Targets are validated (hostname or IP syntax, length limit, no shell metacharacters), the probe set is allowlisted, count and rate are bounded, and the first use of each probe type needs visible consent describing what will be sent.
Sensitive data
Process command lines, socket remote addresses, hosts entries, proxy credentials, Wi-Fi network names and event messages can expose private data. They are shown locally, follow the log-privacy redaction policy in exports, and never include Wi-Fi keys or proxy passwords.
Sampler budget
One shared sampler serves D01.07, D02.09, D10.01, D10.06 and D10.09: bounded interval, bounded ring buffer, history persisted only when the user enables it, paused when no consumer is subscribed.
Cancellation
Every enumeration or probe is cancellable; child processes are killed as a tree.
Event channels
Event Log reads are read-only. Channels needing elevation (for example Security) report needs-elevation and are never silently skipped.
23.2 System services (D10.01–D10.12)
D10.01 — System Pulse Overview Console
• Objective: one console for the machine's present condition. Backend: aggregates the shared sampler (CPU, memory, disk, network totals), uptime, process count, session and pending-reboot indicator where detectable; each tile carries provenance. Frontend: instrument tiles, sample age, drill-down links to D10.03, D10.06, D10.09. Safety: read-only. Acceptance: injected provider yields exactly the shown values; stopping the sampler produces the stale marker within one interval; no tile appears before its first real sample.
D10.02 — Windows Event Log Severity Ledger
• Objective: count and browse events by severity. Backend: reads allowlisted channels (System, Application, others the user enables) through the Event Log API with time range, level and provider filters, paged by cursor; severity counts come from the returned records for the stated range, never estimated. Message text is fetched only for records the user opens. Frontend: severity ledger, time-range picker, record inspector (provider, event ID, record ID, time). Safety: read-only; Security channel is needs-elevation. Acceptance: fixture log with known counts per level reproduces exactly; empty range shows zero with the range stated; an unreadable channel shows denied, not zero.
D10.03 — Active Process Register & Resources
• Objective: a register of running processes and their resources. Backend: PID, parent PID, image name and path (when readable), user, start time, CPU percentage computed from two real counter readings with the interval stated, working set, handle and thread counts. Access-denied fields are labeled. Command line appears only after an explicit expand. Frontend: sortable table, tree by parent, inspector, links to D12.01 for service hosts and to D05 for installed apps. Safety: read-only; no terminate or priority control here (termination would need a later specification with a consent-gated action and protected-process blocklist). Acceptance: fixture process set renders exactly; a process that exits mid-sample is marked ended; protected processes show denied fields, not blanks that read as zero.
D10.04 — System Binary Certificate Inspector
• Objective: inspect the signature of a system binary. Backend: inspectBinary(path) through the signature provider (embedded Authenticode, then catalog lookup): status (valid, invalid, unsigned, untrusted root, expired-but-timestamped), signer, thumbprint, algorithm, timestamp, catalog name. Path is re-authorized in Main and must be an existing regular file. Reports evidence; issues no safe/malicious verdict. Frontend: evidence card with chain, validity period and the statement No verdict is made. Acceptance: fixtures for embedded-signed, catalog-signed, unsigned, tampered and expired-with-timestamp produce the right state; no verdict wording in UI strings.
D10.05 — System Boot & Session Clock Timeline
• Objective: when the machine started and what sessions did. Backend: last boot time and uptime from the OS, logon times, and sleep/resume/shutdown events from the Event Log (labeled by event source). Fast Startup is detected and stated because it makes uptime differ from the last full boot. Frontend: timeline from real timestamps; gaps are gaps. Acceptance: injected event fixture renders at correct offsets across a DST change; Fast Startup fixture shows both clocks with an explanation.
D10.06 — Live Performance Pulse Charts
• Objective: CPU, memory, disk and network over time. Backend: the shared sampler's ring buffer; per-core CPU and per-physical-drive disk where supplied. Frontend: lines drawn only from stored samples, at least two samples before any line, visible gaps when the sampler was off, units and interval stated. Acceptance: chart data equals the stored series exactly; a sleep or clock-change gap is drawn as a gap; no data before the first real reading.
D10.07 — Device Driver Inventory & Signatures
• Objective: installed drivers with signature state. Backend: PnP/driver enumeration (name, provider, version, date, INF name, device class, signer, signature state, device status and problem code); date and version come from the driver record. Frontend: class-grouped table, signature badge, problem-code filter, inspector. Safety: read-only; no install, update or removal. Acceptance: fixture with signed, unsigned and problem-coded entries renders exactly; an absent signer reads unknown.
D10.08 — Event Log Channel Explorer
• Objective: discover and browse channels. Backend: log name, type (admin, operational, analytic, debug), enabled state, maximum size, record count and retention mode where readable. Analytic and debug channels are listed, never enabled or modified. Frontend: channel tree, record count, open-in-ledger link to D10.02. Acceptance: fixture channel set renders exactly; an unreadable channel shows denied.
D10.09 — Top Resource Consuming Processes
• Objective: which processes use the most CPU, memory, disk and network now. Backend: ranking over the same snapshot as D10.03 (shared, not forked), interval stated, deterministic tie order; per-process disk and network figures only where the provider supplies them. Frontend: ranked bars from real values with a metric selector. Acceptance: ranking equals D10.03 for the same snapshot; an unsupplied metric shows unavailable, not zero.
D10.10 — App-to-Process Cross-Service Links
• Objective: connect installed applications to running processes. Backend: joins D05.01 to D10.03 by executable path and package identity; each match records its basis. No fuzzy name matching. Frontend: link badges both ways; unmatched processes stay unmatched. Acceptance: fixture with an app, a packaged app and an unrelated process links exactly the first two; a process with an unreadable path is unmatched (path denied).
D10.11 — System Service Dependency Graph
• Objective: a system-wide view of service dependencies. Backend: the shared SCM enumeration (Section 22.1) and the focus-and-neighbors queries of D12.04; no second enumerator. Frontend: graph centered on a service with depth control, plus a textual list. Acceptance: edges equal D12.04 edges for the same snapshot; read-only.
D10.12 — Unified System Event Timeline
• Objective: one timeline merging Windows events and KNOuX's own journal. Backend: merges Event Log records and KNOuX journal/receipt entries by timestamp, every row labeled with its source; no correlation or cause is asserted unless a record states it. Frontend: filterable timeline with source chips and receipt links. Acceptance: interleaved fixture orders correctly within a stated clock tolerance; source filter returns exact subsets.
23.3 Network services (D10.13–D10.24)
D10.13 — Network Interfaces Console
• Objective: every adapter and its real configuration. Backend: adapter enumeration: name, description, type, status, MAC, link speed, IPv4/IPv6 addresses and prefixes, gateways, DHCP state and lease times, DNS servers, MTU, interface metric, virtual/physical flag. Frontend: adapter list with status badges and a configuration inspector; disconnected and virtual adapters shown and labeled. Safety: read-only. Acceptance: provider-injected topology (Ethernet, Wi-Fi, VPN/virtual, disconnected) renders exactly; an adapter that disappears mid-refresh is marked removed.
D10.14 — DNS Resolver Configuration Dossier
• Objective: how name resolution is configured. Backend: per-interface DNS servers, search suffixes, DNS-over-HTTPS settings where the OS reports them, NRPT/policy rules where readable, and the hosts-file link to D10.22. The resolver cache listing belongs to D11.06; this service does not duplicate it. Frontend: dossier per interface with the effective order stated as reported. Acceptance: fixtures with DHCP-assigned and static DNS render exactly; unreadable policy is labeled partial.
D10.15 — Network Hardware Atlas & NIC Rack
• Objective: the physical and virtual NICs. Backend: adapter hardware records (vendor, model, driver version and date, PCI location, bus type, features such as checksum offload and RSS where the provider reports them), joined to D10.13 by adapter identity. Frontend: rack view of NIC cards; absent fields shown as —. Acceptance: fixture with PCIe, USB and virtual NICs renders exactly; a join with no matching adapter is shown as unmatched.
D10.16 — Connectivity Diagnostic Step Sequence
• Objective: step-by-step connectivity diagnosis. Backend: a fixed, ordered probe sequence: adapter up, gateway reachable (ICMP), DNS server reachable, name resolution of a user-chosen or default name, outbound connection check to a documented endpoint. Each step records its probe, target, result, duration and error class and stops or continues by an explicit rule. Probes are bounded and cancellable. Frontend: sequence that advances only on real step results; a failed step shows evidence, not a diagnosis the evidence does not support. Safety: active probe (Section 23.1); consent on first use. Acceptance: simulated network with failures at each step stops at the right step with the right evidence; no step advances on a timer; cancel terminates in-flight probes.
D10.17 — Real-Time Traffic & Throughput Chart
• Objective: throughput per interface over time. Backend: interface byte counters sampled at a bounded interval; rate = counter delta ÷ real elapsed time, with counter wraparound and interface reset handled and flagged. Frontend: chart from stored samples only, per-interface selector, units stated. Acceptance: injected counters produce the exact rates; a counter reset is a flagged gap, not a negative or spiked value.
D10.18 — Hop Route & Latency Visualizer
• Objective: the route to a host and latency per hop. Backend: allowlisted trace with validated target, max hops and per-hop timeout; each hop records address, optional reverse-DNS name, per-attempt RTTs, and loss. Non-responding hops are shown as no response, not as failure of the route. Frontend: hop list and latency bars from real RTTs. Safety: active probe; consent on first use. Acceptance: simulated trace with a silent hop and a latency spike renders exactly; invalid target rejected with a positioned error.
D10.19 — LAN Topology & Node Relationship Map
• Objective: what the machine can see on its local network. Backend: the ARP/neighbor table and gateway information, optionally a bounded, consented local-subnet reachability sweep. Output is explicitly partial by nature: it lists neighbors the OS has cached or that answered. Device names and vendors come only from sources that supplied them (for example a MAC vendor prefix, labeled as such). Frontend: map of the local node, gateway and observed neighbors, with a standing statement This is not a complete network inventory. Safety: passive by default; any sweep needs consent, a subnet-size cap and cancellation. Acceptance: fixture neighbor tables render exactly; no node appears that no source reported; the incompleteness statement is always visible.
D10.20 — Active Socket & Port Explorer
• Objective: open ports and connections with their owners. Backend: TCP and UDP tables with local and remote endpoint, state, owning PID joined to D10.03, and listening-versus-established classification. Owner resolution failures are labeled. Frontend: filterable table (port, state, process, protocol), link to the process. Safety: read-only; no connection can be closed from here. Acceptance: fixture socket table with a listening port, an established connection and an ownerless entry renders exactly.
D10.21 — Wireless Wi-Fi Status & Signal Instrument
• Objective: the current Wi-Fi link. Backend: WLAN interface state: SSID, BSSID, radio type, channel, band, receive/transmit rate, signal quality as reported, and visible-network list when the OS permits scanning. Location permission requirements for SSID access are detected and stated. No radio or no adapter is unsupported-platform with the reason. Frontend: signal instrument drawn from the reported quality value and a stored sample series. Safety: read-only; saved profile keys are never read. Acceptance: injected profiles (connected, disconnected, no radio, permission-denied) render the right state; no signal value without a provider reading.
D10.22 — Windows Hosts File Inspector
• Objective: inspect the hosts file safely. Backend: reads the hosts file as text, parses entries (address, names, comments), flags malformed lines, duplicate names, and entries that redirect well-known names, with the rule shown. Frontend: parsed table and raw view. Safety: read-only here; editing is out of scope unless a later specification adds elevation, backup and journaling. Acceptance: fixture hosts files (comments, duplicates, malformed, IPv6, very large) parse to the exact entries; read failure is classified.
D10.23 — Proxy & WinHTTP Configuration Graph
• Objective: show how traffic is proxied. Backend: WinINET per-user settings (manual proxy, PAC URL, auto-detect), WinHTTP machine proxy, and environment proxy variables, each labeled by source; precedence is described as documented, not asserted as the effective result unless the OS reports it. Credentials embedded in proxy URLs are redacted. Frontend: graph of sources and the values each reports. Acceptance: fixture with differing per-user and machine proxies renders both; a URL with credentials is displayed redacted.
D10.24 — Network Recovery & Reset Gateway
• Objective: gated network recovery actions. Backend: a gateway to allowlisted operations that already exist in the Repair Lab contract (DNS flush D11.06, Winsock reset reviewed in D11.07, TCP/IP reset reviewed in D11.08, adapter disable/enable for a selected adapter, DHCP renew/release). It adds no new command surface. Every action requires the Repair Lab preview, the pre-change configuration snapshot saved to the receipt, operation-specific consent, elevation detection and the recovery statement of Section 21.3; reset operations may require a restart and say so. Frontend: action cards with risk class, the diff from D11.08 where applicable, and the standing note that a reset removes custom configuration and layered providers. Safety: H. Acceptance: simulated runner proves the exact command sequence and snapshot capture; refusal without consent; non-elevated launch reports needs-elevation without running; real execution only with explicit authorization.
23.4 Hardware services (D10.25–D10.36)
D10.25 — Device Hardware Atlas & Components
• Objective: a map of the machine's components. Backend: system manufacturer, model, serial (shown only after an explicit expand), BIOS vendor/version/date, baseboard, chassis type, and a component index linking to D10.27–D10.35. Fields come from SMBIOS/CIM and are tagged with their reader. Frontend: atlas with component cards; absent fields —. Acceptance: fixture machines (desktop, laptop, virtual machine) render exactly; a virtual machine is labeled as such.
D10.26 — Battery Charge & Health Instrument
• Objective: current battery state. Backend: presence, charge percentage, charging/discharging/AC state, estimated runtime as reported by the OS, voltage and rate where available. No battery is unsupported-platform (desktop), not an error. Frontend: instrument from reported values and a stored sample series. Acceptance: injected profiles (charging, discharging, absent, unknown runtime) render correctly; runtime is never computed by KNOuX.
D10.27 — Processor Architecture & Core Die
• Objective: CPU facts. Backend: name, vendor, architecture, physical cores, logical processors, base and current clock as reported, cache sizes where reported, instruction-set features the OS exposes. Frontend: core map from the real core/thread counts; hybrid core types are shown only where the provider reports them. Acceptance: fixture CPUs (hybrid, SMT on/off, virtualized) render exactly; unreported cache shows —.
D10.28 — Graphics Adapter Bay & VRAM
• Objective: GPUs and their memory. Backend: adapter name, vendor, driver version and date, dedicated and shared memory as reported by the graphics subsystem (note that some interfaces cap or misreport dedicated memory, and the reader used is shown), active output, integrated versus discrete where determinable. Live utilization appears only where a counter exists. Frontend: adapter cards; software/basic adapters labeled. Acceptance: fixture with integrated plus discrete adapters renders exactly; missing utilization counters read unavailable.
D10.29 — DIMM RAM Slots & Memory Layout
• Objective: physical memory layout. Backend: installed capacity, per-module capacity, speed, type, form factor, manufacturer, slot locator and populated/empty slots where SMBIOS reports them; total slot count only when reported. Live memory use links to D10.01. Frontend: slot strip from the reported slots. Acceptance: fixtures with partially populated slots and a virtual machine (no SMBIOS memory detail) render honestly; no slot appears that SMBIOS did not report.
D10.30 — Battery Wear & Cycle Count Ledger
• Objective: battery wear. Backend: design capacity, full-charge capacity and cycle count from the OS battery report/IOCTL where exposed; wear is the reported ratio, computed only when both capacities exist and shown with its inputs. Cycle count is absent when the firmware does not expose it. Frontend: ledger of stored readings over time. Acceptance: injected values compute the exact wear ratio; missing cycle count shows unavailable; no history before real readings.
D10.31 — Thermal Sensors & Temperature Board
• Objective: temperatures the OS exposes. Backend: ACPI thermal zones and any storage or GPU temperatures reachable without vendor tools, each with its source and sample time. Most consumer machines expose little or nothing through the standard providers; the service states this and does not load third-party kernel drivers to obtain more. Frontend: board listing only sensors that reported; a clear no standard sensors exposed state otherwise. Acceptance: injected sensors render exactly; zero sensors renders the honest empty state; no synthetic temperature exists anywhere in fixtures presented as measurements.
D10.32 — Physical Disk Drives & Bus Interface
• Objective: physical disks and how they connect. Backend: model, serial (expand-to-show), firmware, size, media type, bus type (NVMe, SATA, USB, virtual), partition style, health status as reported, and link to D07.01/D07.09. Frontend: drive cards; bus type shown only as reported. Acceptance: provider-injected NVMe, SATA, USB-bridged and virtual disks render exactly; an unreported field reads —.
D10.33 — USB Controller & Device Topology Tree
• Objective: the USB tree. Backend: controllers, root hubs, hubs and devices with vendor/product IDs, names, class, speed as reported, port path and connection state through PnP enumeration; hot-plug events update the tree. Frontend: tree with device inspector and a textual list alternative. Acceptance: fixture tree with hub nesting and a hot-plugged device updates within one refresh; devices with problem codes are flagged as reported.
D10.34 — Monitor Topology & Resolution Canvas
• Objective: monitors and their geometry. Backend: display configuration: per-monitor resolution, refresh rate, position in the virtual desktop, primary flag, orientation, scaling percentage, color depth, connection type and EDID-derived name/manufacturer where readable. Frontend: canvas drawn from the reported rectangles in true proportion. Acceptance: fixture with two monitors of different resolution and negative-offset positions renders in the exact geometry; a single-monitor and remote-session case are handled.
D10.35 — Audio Endpoint Mixer & Devices
• Objective: audio devices and their state. Backend: playback and capture endpoints with name, state, default flags, format and current volume/mute as reported. Frontend: endpoint list with read-only meters; volume and mute changes are not offered unless a later specification adds typed, verified controls. Acceptance: fixture endpoints (default, disabled, unplugged) render exactly; no level appears without a provider reading.
D10.36 — Hardware Evidence & Diagnostic Report
• Objective: one exportable hardware report. Backend: assembles D10.25–D10.35 outputs at one capture time, each section stating its provider and any unsupported or absent fields; serial numbers and identifiers are excluded from exports by default and included only by explicit choice. Export formats: Markdown, JSON, HTML. Frontend: report preview with section completeness markers. Acceptance: report content equals the underlying service outputs for the same capture; an unsupported section appears as such, not omitted; default export contains no serial numbers.
Volume 5 — Applications, Automation, Google Workspace, Settings / AI
24. Domain 05 — Applications (12 entries)
Applications is the software-management center: a truthful inventory of what is installed, who published it, how it is signed, what it occupies, what it adds at startup, and a gated path to update or remove it. Most entries are observation. The action entries (D05.06, D05.08, D05.10) delegate to the application's own uninstaller or to winget; KNOuX never deletes an application's files or registry keys itself.
24.1 Shared Applications rules (REQUIRED)
• One inventory. A single provider builds the application inventory and serves D05.01–D05.12, D02.08, D01.03 and D10.10. Sources, each independently reported: uninstall keys under HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\Uninstall, the 32-bit view (WOW6432Node) and HKCU equivalents; packaged apps (Appx/MSIX) through the package manager API; and, where present, winget list correlation. A failed source is shown as failed, never as an empty source.
• Normalized record. {appId, name, version, publisher, installDate, installLocation, estimatedSize, uninstallCommand, quietUninstallCommand, source, scope (machine|user), architecture, packageFamilyName?, productCode?, wingetId?}. A field the source did not supply is absent. estimatedSize is labeled as reported by the installer until KNOuX measures the folder itself (D05.09). Stable appId derives from source plus key or package full name, so it survives restarts.
• Deduplication, not deletion. The same product registered in several views is shown once with all registrations listed. Entries marked as system components, updates or hidden by the installer are classified, not discarded; the filter default may hide them and states that it does.
• Untrusted registry text. UninstallString, DisplayIcon and InstallLocation are written by third-party installers. They are parsed into executable and arguments, environment variables are expanded, and nothing from them is executed without the validation in D05.06. They are never passed to a shell.
• winget availability. winget is a separate component and may be absent, outdated or blocked by policy. Detect version and source health first; if absent, D05.08 and D05.10 report provider-missing with the reason. winget output is localized and version-dependent, so output parsers are tested against recorded real outputs per supported winget version, and an unparseable output is UNKNOWN with raw text attached, never a guess. Prefer a structured interface (the supported PowerShell module or COM API) where verified to exist, and record that decision; otherwise parse the CLI with fixtures.
• Elevation. Per-machine installs and uninstalls usually need elevation. Detect it before starting; never self-escalate silently.
• No rollback promise. KNOuX cannot reverse a third-party uninstaller. The UI states this on every removal preview and offers a restore-point attempt (D11.11) when System Protection is on.
• Logos and icons. Icons come from the installed binary or package manifest through a read-only icon extractor with a size bound; a missing icon shows a neutral type glyph, never another app's icon.
24.2 Per-service contracts
D05.01 — Installed Applications Register
• Objective: the authoritative list of installed software. Backend: the shared inventory with snapshot time, per-source status and counts. Frontend: sortable, filterable table with icon, name, version, publisher, size, install date, scope, source badges; inspector with every registration and raw uninstall fields; virtualized for thousands of rows. Safety: read-only. Acceptance: registry-fixture and package-fixture inventories (machine, user, 32-bit, MSIX, hidden update entry, entry with no publisher) produce exactly the expected records; counts equal ground truth; a denied hive shows denied, never zero.
D05.02 — App Identity & Authenticode Trust
• Objective: show who signed an application's main binary. Backend: resolves the primary executable (from the registration, install location or package manifest), then uses the signature provider shared with D10.04 and D06.12: status, signer, thumbprint, timestamp, and for packages the package signature. Resolution failures are reported (executable not found). Evidence only; no safe/malicious verdict. Frontend: identity card with the evidence chain and No verdict is made. Acceptance: fixtures: signed, unsigned, tampered, expired-with-timestamp, MSIX-signed, missing executable; each yields the expected state and the missing-executable case is not reported as unsigned.
D05.03 — Multi-Parameter Software Search
• Objective: find applications by several attributes at once. Backend: an in-memory index over the inventory with a typed query language (name:, publisher:, version:, size:, installed:, scope:, signed:, source:, free text), parse errors with positions, no code execution. Results are identical to the equivalent GUI filter. Frontend: query bar, filter chips, result list with highlights. Acceptance: query-to-filter equivalence tests; range queries on size and date at boundaries; malformed queries produce positioned errors.
D05.04 — Publisher Intelligence & Reputation
• Objective: understand a publisher from evidence KNOuX can observe. Backend: groups apps by signer identity (not by display string), and reports how many apps share it, signer certificate details, first-seen time in the KNOuX inventory, and distinct products. Reputation is local evidence only (signature validity, consistency across the machine). Any external reputation lookup is optional, off by default, requires visible consent describing exactly what is sent (a signer name or hash, never file contents or paths), reports its provider and time, and when absent the UI says no external reputation source is configured. KNOuX invents no reputation score. Frontend: publisher cards with evidence and provenance labels. Acceptance: two apps with different display names but one signer group under one publisher; the same display name with different signers stays separate; with no external source configured, no reputation figure exists anywhere.
D05.05 — Recently Changed Applications
• Objective: what was installed, updated or removed lately. Backend: install date where the source reports it, plus differences between successive KNOuX inventory snapshots (added, removed, version changed) labeled observed between snapshots with both times; Windows Installer and servicing events from the Event Log are used only where they state the change. An app with no reported date is listed as date unknown, not given the scan date. Frontend: timeline grouped by change type. Acceptance: snapshot-pair fixture reports exactly the injected additions, removals and version changes; unknown dates are not placed on the timeline.
D05.06 — Bulk Uninstall Queue & Batch Manager
• Objective: queue several removals and run them in a controlled sequence. Backend: queueUninstall(appIds) builds a typed plan; previewUninstall shows, per app, the exact method (MSI product code via the Windows Installer service, the app's own uninstaller with its own UI, winget uninstall by id, or package removal for MSIX), elevation need, whether the uninstaller is interactive, and the standing no-rollback statement. Rules: the executable must exist, resolve to an absolute path, and be a regular file; MSI product codes are validated as GUIDs and the argument vector is built by KNOuX, never taken from registry text; silent mode is used only when the installer registered a quiet command or the method is MSI/winget, and the UI says so. System components and protected apps (Windows, drivers, security products) are not queueable. Execution is sequential with a timeout per item, cancellation between items (a running third-party uninstaller is not force-killed by default; the user is told), exit-code capture, and post-verification (registration gone, package absent). The plan hash and approval token work as in Section 9.3. Frontend: queue with per-item state (waiting, awaiting user in uninstaller, running, verified removed, failed, cancelled), batch receipt. Safety: H; no silent bulk removal without approval of the exact queue. Acceptance: simulated runner proves the exact argument vectors, ordering, timeout, cancellation between items and post-verification; a protected app is refused in Main; a queue edited after approval invalidates the token; a mismatch between exit code and registration state is VERIFY_FAILED.
D05.07 — Orphaned Leftover Trace Analysis
• Objective: find traces of applications that are no longer installed. 25. Domain 13 — Automation Flow Studio (12 entries)
Automation Flow Studio runs KNOuX services on a schedule or trigger. Its first rule: a workflow is not active because a draft or a schedule exists. A workflow becomes active only through an explicit, hash-bound approval, and every run goes through the same plan, consent, journal and verification path as the manual service it calls. Earlier Codex branches are recorded (SUPPLIED) as holding verified automation execution work; Codex locates and preserves it before adding anything (NOT VERIFIED).

25.2 Shared Automation rules (REQUIRED)
• Execution ownership. One scheduler component in Electron Main owns triggering and run state. It computes next-run instants in the workflow's IANA timezone with correct handling of DST gaps (a nonexistent local time runs at the next valid instant, stated) and overlaps (an ambiguous local time runs once, stated), and persists nextRun so it survives restart.
• Background constraint. Scheduled runs occur only while KNOuX (or its documented background helper, if the architecture has one) is running. The UI states plainly what happens when the application is closed or the machine is asleep, according to the missed-run policy. KNOuX does not claim operating-system-level scheduling unless a registered scheduled task actually exists and is verified (D13.02).
• Duplicate-run prevention. A per-workflow lock with an idempotency key (workflowId, scheduledInstant). A second trigger while a run is active is skipped with a reason and logged. A crash leaves a stale lock that is reconciled on launch by inspecting the run journal.
• Hash binding. Before each run and each step, the current definitionHash, scope hash and step parameters are compared with the approved values. Any difference makes the run skipped (needs reapproval); it is logged and shown in Pending Safe Actions (D01.12), never executed.
• Dry run. Every workflow has a dry run that calls each step's preview path and records predicted outcomes; it changes nothing.
• Gating order. Quiet hours, power state, conditions, then the run. A gated run records the gate and the next eligible instant.
• Cancellation and recovery. Cancel stops dispatching new steps and cancels the in-flight operation through its own cancellation contract; interrupted runs are marked on launch with exact per-step truth from the underlying receipts.
• Journal. Append-only, checksummed run records; history views read only from it.
• Honest states. Draft, Active, Paused, Needs reapproval are visually and semantically distinct; the next-run preview appears only for Active workflows.

26. Domain 04 — Google Workspace (10 entries)
Google Workspace connects KNOuX to a user's own Google account. Every service here depends on an external account and on credentials KNOuX does not hold, so the first deliverable is an honest capability state (needs-credential, then needs-consent, then available) and the second is a complete, tested integration up to that boundary. 26.1 Shared Google rules (REQUIRED)
Topic
Requirement
Credential boundary
A Google Cloud OAuth client (client ID, and secret only if the chosen client type issues one) is a configuration input, not source code. Missing → every D04 service reports needs-credential with the exact configuration key names and where they go, and Codex adds the item to the handover under Blocked on owner input. Codex never invents, hardcodes or guesses client values.
Authorization flow
OAuth 2.0 authorization-code flow for an installed application with PKCE and a loopback redirect on an ephemeral port, opened in the user's default browser (never an embedded webview). The state value is verified; the code verifier never leaves Main.
Scope discipline
Request the narrowest scope each feature needs, incrementally, at the moment of first use. Prefer drive.file or Picker-granted access over broad Drive scopes, and read-only scopes over read-write for any feature that only reads. Sensitive and restricted scopes (Gmail, Contacts, broad Drive) can require Google's app verification before ordinary users can grant them; that is an external prerequisite documented in the handover, not a code defect. The exact scope list is a table in the integration document and every scope has a named feature.
Token handling
Access and refresh tokens live only in Main, encrypted with the OS-protected secret store. They never reach the renderer, logs, journals, receipts, exports, crash reports or fixtures. Refresh happens in Main with single-flight protection; a refresh failure moves the account to needs-reauthorization. Disconnect revokes the token at Google's revocation endpoint, deletes local copies and clears cached data, and reports revocation failure honestly.
Account identity
The connected account's email and ID, as returned by Google, are shown. Account types differ: consumer accounts, Workspace accounts, and Workspace accounts whose administrators restrict third-party apps. Eligibility errors are mapped to specific messages.
API behavior
Typed clients with request validation, pagination through page tokens with a bounded page count, fields partial-response masks, exponential backoff with jitter on 429 and 5xx, Retry-After honored, quota and rate errors surfaced as such, request deadline, cancellation, and idempotency keys or conditional writes where the API supports them. Offline or disconnected states are distinct from API errors.
Write operations
Anything that creates, edits or deletes data in the user's Google account is preview-first: the exact change is shown, consent is operation-specific, and the result is verified by reading the resource back. Deletion is out of scope unless a service below says otherwise.
Data minimization
KNOuX reads metadata and content only for the resources the user selects or the feature needs. Mail and contact content is not stored beyond a bounded cache, is never sent to an AI provider without a separate explicit consent for that exact data, and is purged on disconnect.
Test doubles
Automated tests use a local mock OAuth and API server that is clearly labeled as a test double, recorded fixtures of real response shapes, and contract tests against the typed clients. Evidence labels such runs mock. A live-account run is possible only with real credentials and is labeled live.
Verification status
Statuses allowed per service: needs-credential, needs-consent, needs-reauthorization, available, partial (some scopes granted), blocked-by-admin-policy, unsupported-account-type.

27. Domain 14 — Settings / Engine / AI (8 entries)
Settings is where preferences, provider credentials and safety guards live. Its governing rule: every control either changes real behavior or is gated with a truthful reason. A toggle with no wired effect is a defect, not a setting; if a control cannot be wired in this slice it is disabled and listed in the handover. Visual customization (D14.05) and layout fidelity remain Codex's stream; this chapter specifies persistence, effects, credentials and routing.
27.1 Shared Settings rules (REQUIRED)
• Persistence. One schema-versioned settings store with atomic writes, checksum, tested forward migrations and a rollback copy of the previous version. Unknown future keys are preserved, not dropped. A corrupt file is detected, the last good copy is restored, and the user is told.
• Validation and defaults. Every setting has a type, bounds, a secure default and a validator in Main. The renderer cannot write a value Main would reject.
• Effect registry. Each setting declares its effect owner (the module that reads it live) and a test that proves the behavior changes. Settings without an owner are not shown as active.
• Secrets. Provider keys and tokens use the OS-protected secret store from Main, are write-only from the renderer (the UI can set or delete one and sees only a masked tail, never the value), and are excluded from logs, journals, receipts, exports and crash reports by construction. Backup/export excludes secrets by default.
• Capability status per provider. AI providers, Google and any other external dependency show needs-credential, needs-consent, available or an error state with a reason; nothing displays connected without a verified call.
• Reset. Reset-to-defaults previews exactly what changes, requires confirmation, never deletes receipts, journals, vaults or secrets unless the user separately chooses so, and is itself journaled.

18. Domain 07 — Storage (12 entries)
Storage explains where capacity goes and what could be reclaimed, using real Windows volume data and authorized analysis. It never implies that bytes are free when they are not.
18.1 Shared Storage rules (REQUIRED)
• Volume truth. Used, free and total come from the volume itself (the filesystem's reported values), per volume, with filesystem type, drive kind (fixed, removable, network, virtual/VHD, optical) and read-only flag. Values are timestamped and are never derived from KNOuX scans. Where the provider cannot report a value, the field is absent with a reason.
• Analysis vs capacity. Folder analysis (D07.02–D07.06) covers only authorized scope and reports its own coverage (bytes analyzed vs volume used). The gap is shown as unanalyzed, never silently attributed to files.
• Allocated vs logical size. Where the provider exposes it, sizes distinguish logical size from size on disk (compression, sparse files, cluster slack, hardlinks counted once). When it does not, the UI states which is shown.
• Reclaim honesty. Reclaimable estimates are sums of measured sizes of specific candidates. Quarantine on the same volume frees zero physical capacity until the quarantine is purged; copying to another volume then removing frees space only after verification. Every reclaim figure states which of these applies. No invented savings.
• Cancellation and caching. Analyses are cancellable, cached per scope with a snapshot time, and invalidated by change detection or user refresh. Treemap and ranking views read the same snapshot so numbers reconcile across D07.02–D07.06 and D06.
• Drive-type honesty. SSD, HDD, removable and virtual volumes differ in available telemetry; the UI shows the capabilities that exist for that drive and labels the rest unsupported with the reason.
18.2 Per-service contracts
D07.01 — Volume Bays & Partition Manager
• Objective: a truthful map of volumes and partitions. Despite Manager in the name, the REQUIRED scope is read-only discovery: disks, partitions (style GPT/MBR, type, size, offset), volumes (letter, label, filesystem, used/free/total, health status), mount points, BitLocker status where readable, system/boot flags. Partition create, delete, format or resize are out of scope and must not exist unless a separate specification adds them with elevation and typed consent. Frontend: bay cards per volume with exact capacity bars from real values, partition strip per disk with real extents, details inspector, hot-plug refresh; unavailable fields shown as — with reason. Acceptance: provider-injected topology (multi-disk, hidden recovery partition, unlettered volume, mount-point volume) renders exactly; a removable disk added or removed updates within one refresh; no write control exists in UI or IPC.
D07.02 — Heavy-File Storage Ledger
• Objective: ledger of the largest files per volume/scope. Backend: the shared ranking from D02.04/D06.10 with per-volume totals, share of analyzed bytes, and age classification. Frontend: ledger table with number-first presentation, filter by volume, handoff to D08 preview. Acceptance: identical ordering to D02.04 on the same snapshot; per-volume totals reconcile to the snapshot.
D07.03 — Byte-Exact Duplicate Hash Groups
• Objective: duplicate groups across volumes within authorized scope. Backend: the D02.03 pipeline, extended with cross-volume grouping and a per-group note when members sit on different volumes (cross-volume duplicates reclaim on the volume where the removed copy lives). Frontend: groups with member volume labels, keep-recommendation, reclaimable bytes per volume. Safety: read-only. Acceptance: cross-volume fixture gives per-volume reclaim figures that sum to the group total; hardlinks excluded.
D07.04 — Interactive Storage Space Treemap
• Objective: see space as nested rectangles. Backend: storageTree(scope, depth) returns a size-annotated directory tree from the snapshot, with a node-count ceiling: nodes smaller than a threshold are aggregated into a labeled other (N items) node whose count and bytes are exact. Layout (squarified algorithm) is computed from real byte values; rectangle area is proportional to bytes, deterministically. Frontend: zoom-in on directories, breadcrumb, hover/inspector with exact size and share, keyboard navigation, color by category or age; tiny nodes are aggregated visibly, never hidden. Acceptance: sum of child areas equals parent area within rounding; aggregated node counts reconcile to ground truth; a 1M-entry fixture renders within the ceiling without exceeding memory bounds; layout identical for identical input.
D07.05 — Folder Ranking Waterfall
• Objective: which folders account for the most bytes. Backend: ranked folder sizes (inclusive and exclusive), cumulative share. Frontend: a waterfall-style cumulative view drawn from the ranked values (steps equal the folder sizes, running total shown), with the remainder bar labeled all others so the total equals analyzed bytes. Acceptance: cumulative total equals analyzed bytes exactly; inclusive vs exclusive toggle consistent with the treemap tree.
D07.06 — Storage Byte Distribution by Category
• Objective: bytes by file category. Backend: category aggregation on the snapshot; categories match D06.08 definitions (single classifier). Frontend: distribution chart plus table; click filters to Files. Acceptance: category sums equal analyzed bytes; classifier changes propagate to both D06.08 and D07.06.
D07.07 — Drive Coverage & Scan Dashboard
• Objective: show how much of each volume has actually been analyzed. Backend: coverage = analyzed bytes ÷ volume used bytes, per volume, with last-scan time and scope list; excluded and protected areas appear as not analyzed. Frontend: per-volume coverage bars with exact figures, scan history, rescan actions; never rounds coverage up. Acceptance: coverage values reproduce from snapshot and volume data; protected exclusions appear as unanalyzed.
D07.08 — Drive Optimization & TRIM Dossier
• Objective: report optimization-relevant facts. Backend (read-only): media type (SSD/HDD where reported), TRIM/retrim support state as reported by the OS, last optimization time and recommended action as reported by the system's own optimization facility, fragmentation level only where the OS provides an analysis result for HDDs. KNOuX does not invent fragmentation or wear numbers. Running optimization is not required; if later added it is an allowlisted, elevated, consent-gated operation recorded in the journal. Acceptance: provider-injected SSD and HDD profiles show appropriate fields; a volume with no data reports unavailable, not a default.
D07.09 — Disk Reliability & S.M.A.R.T. Health
• Objective: surface the reliability data Windows exposes. Backend: storage reliability counters (temperature, wear, power-on hours, read/write error counts, predictive-failure flag) where the driver exposes them; S.M.A.R.T. attributes only where reachable without vendor tools. NVMe, SATA, USB bridges and RAID controllers differ; support is detected per disk and shown. No health score is invented: the UI shows the raw reported values with units and the OS's own predictive-failure state. Frontend: per-disk instrument cards, each field flagged reported or unsupported. Acceptance: injected profiles for NVMe, SATA and USB-bridged disks (the last unsupported) render correctly; no field appears without provider data.
D07.10 — Storage Reclaim Planner & Basket
• Objective: assemble candidates from Smart Scan, duplicates, large files and cleanup into one reviewed basket and hand it to Cleanup. Backend: the basket holds references (file identity + path + size at add time), deduplicates across sources, rechecks existence and size at review, and computes three separate numbers: bytes in basket, bytes physically freed immediately if the chosen method is permanent removal, and bytes freed only after a later quarantine purge (zero immediately). It hands off a draft Cleanup plan (D08.05) with a plan hash. Frontend: basket with per-item real sizes, a method selector reflecting the three numbers, clear statements; no execution here. Acceptance: adding the same file from two sources yields one entry; a file changed after adding is flagged; same-volume quarantine shows 0 freed now; numbers reconcile.
D07.11 — Capacity Trend Timeline
• Objective: capacity over time. Backend: persists periodic real volume samples (used/free/total, timestamp) at a bounded interval and on scan completion; retention rolls old samples into daily summaries. Frontend: line drawn from stored samples only; at least two samples before any trend is drawn; gaps shown as gaps; a days-to-full projection appears only when a stated minimum span exists and is labeled estimate from observed trend with its basis. Acceptance: stored series equals rendered series; clock changes and sleep gaps are handled; no backfill.
D07.12 — Removable USB & External Volume Dock
• Objective: awareness of removable and external volumes. Backend: hot-plug events, volume identity (serial/GUID), label, filesystem, free/total, read-only flag, authorized-source status for sources that live on the device. Safe-eject is not implemented by KNOuX unless specified and verified; the UI links to the OS action. Operations in progress on a removable volume are surfaced before it is removed. Frontend: dock of connected volumes with real values, a warning when an active session or plan references the volume, an honest disconnected state for known-but-absent volumes. Acceptance: plug/unplug fixtures update the dock; a plan whose destination volume disappears is marked stale and blocks execution; re-insertion restores authorized-source status only if identity matches.
